# Database foundation

The first reviewed revision is `0001_initial_postgis`. It creates the existing core tables, PostGIS polygon/point columns with GiST indexes, private versioned radar artifact metadata, and permitted area-level classification records. Large rasters stay in private object storage; only their URI and checksum enter the database. It does not create public tile access.

For a **new empty PostGIS database**, inspect the target connection and back it up, then run `python -m alembic -c backend/alembic.ini upgrade head` (or `python -m scripts.initialize_database`). Check `alembic_version`, PostGIS extension, table list, geometry SRIDs, indexes, and representative inserts. For rollback on a disposable new database, run `python -m alembic -c backend/alembic.ini downgrade base`; this drops the application tables and data but leaves the PostGIS extension. Never run downgrade on a populated database without a reviewed backup and data plan.

An existing database made with the old `Base.metadata.create_all` helper has no Alembic version and may contain these tables. Do not run this initial migration or stamp it blindly against that database. Compare its schema and data to this revision, then plan a separate baseline or data migration. Offline `upgrade head --sql` verifies SQL generation only; it does not prove PostGIS execution or production safety. The new radar tables are storage foundations, not an active ingestion or publication path.
