# Database foundation

The migration chain begins with `0001_initial_postgis`. It creates the core tables, PostGIS polygon/point columns with GiST indexes, private versioned radar artifact metadata, and permitted area-level classification records. Revisions `0002` through `0005` add contract values, alerts/source status, briefs, and audited administration/review/job state. `0006_agent_outputs` adds the restricted PostGIS tables populated by `scripts/load_agent_outputs.py` for reviewed incident rankings, role-specific recommendations, insights, budgets, and building context. Large rasters stay in private object storage; only their URI and checksum enter the database. None of these revisions creates public tile access.

For a **new empty PostGIS database**, inspect the target connection and back it up, then run `python -m alembic -c backend/alembic.ini upgrade head` (or `python -m scripts.initialize_database`). Check `alembic_version`, PostGIS extension, table list, geometry SRIDs, indexes, and representative inserts. For rollback on a disposable new database, run `python -m alembic -c backend/alembic.ini downgrade base`; this drops the application tables and data but leaves the PostGIS extension. Never run downgrade on a populated database without a reviewed backup and data plan.

An existing database made with the old `Base.metadata.create_all` helper has no Alembic version and may contain these tables. Do not run this initial migration or stamp it blindly against that database. Compare its schema and data to this revision, then plan a separate baseline or data migration. Offline `upgrade head --sql` verifies SQL generation only; it does not prove PostGIS execution or production safety. The radar and agent-output tables are storage foundations, not an active public publication path. The `0006` revision has not been live-PostGIS verified as part of the M4 integration.
